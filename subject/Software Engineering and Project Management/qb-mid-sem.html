THEORY · Q1

Software ki nature aur SE principles

QUESTION

Explain the nature of software and the fundamental principles of Software Engineering.

ANSWER

Software ki nature hardware se bilkul alag hai — isi nature ki wajah se Software Engineering chahiye. Pehle characteristics samjho:

  • Intangible hai: chhua nahi ja sakta; sirf code, documents aur behaviour se samajh aata hai. Isliye progress measure karna mushkil hota hai.
  • Manufacture nahi hota, develop hota hai: hardware factory mein banta hai, software ek baar develop hokar copy hota hai. Cost design mein hai, production mein nahi.
  • Physically wear out nahi hota: time ke saath ghista nahi, par environment badalne (OS, hardware, needs) se outdated/fail hota hai — is curve ko “bath-tub nahi, obsolescence” samjho.
  • Complexity aur change: aaj ke systems laakhon lines ke hote hain aur requirements hamesha badalti hain — bina engineering discipline ke unmanageable ho jaate hain.

Fundamental principles (exam mein ye 4–5 pakke likho):

  • Separation of concerns: badi problem ko chhote independent parts mein todo (modularity ki buniyaad).
  • Abstraction: detail chhupakar sirf zaroori view dikhao (jaise function ka naam, andar ka code nahi).
  • Modularity + information hiding: har module ek kaam kare, apna internal data chhupaye.
  • Incremental + iterative development: chhote pieces mein banao, feedback lo, sudharo.
  • Documentation aur measurement: decisions likho, progress measure karo — bina iske control impossible hai.
  • Reusability: libraries, APIs, frameworks dobara use karo — time bachta hai, defects kam hote hain.
  • Maintainability: software aisa design karo ki bug fix, feature addition, performance aur security updates bina rewrite ke hon.

Reference examples pakke karo: manufactured vs developed — laptop manufacture hota hai, par Windows/Android/banking app develop hoti hai (cost design + maintenance mein hai). Wear-out: hardware heat/stress/age se ghista hai; software modify hone par bigadta hai (nayi feature → unexpected bug → aur modification). Abstraction: sort(data) use karte waqt andar ka algorithm jaanne ki zarurat nahi. Complexity: e-commerce app mein UI, auth, product, payment, order, database, notification services — is management ke liye hi SE chahiye.

EXAM DEFINITION

Software Engineering is the systematic, disciplined, quantifiable approach to the development, operation, and maintenance of software.

Exam-ready plan: pehle 4 characteristics (intangible, developed-not-manufactured, no physical wear, complexity/change), phir 4–5 principles with one-line meaning, end mein SE definition. Characteristics + principles dono maange gaye hain — ek bhi chhoota toh aadhe marks gaye.

Mitchell wali formal definition bhi likh sakte ho: Task T, Performance measure P, Experience E — E ke saath T par P improve ho toh program learn kar raha hai (jaise T = spam pehchanna, P = accuracy, E = labeled emails).

THEORY · Q2

Generic + prescriptive process models

QUESTION

Explain the generic process model and different prescriptive process models.

ANSWER

Generic process model har software process ka common framework hai — 5 activities: communication (requirements samjho), planning (schedule/resources), modeling (design banao), construction (code + test), deployment (deliver + feedback). Har prescriptive model inhi 5 ko alag flow mein arrange karta hai.

Prescriptive models (har ek: flow + best-for + weakness):

  • Waterfall: strictly sequential — ek phase complete, tabhi agli. Best jab requirements fixed aur clear hon (jaise payroll system). Weakness: change costly, working software end mein milta hai.
  • Incremental (RAD): software tukdon (increments) mein deliver hota hai; har increment working subset hai. RAD mein components + time-boxing se fast delivery. Best jab early partial delivery chahiye.
  • Evolutionary (Prototyping/Spiral): prototype banao → feedback → refine; ya spiral mein har loop mein risk analysis. Best jab requirements unclear hon.
  • Unified Process (UP): use-case driven, architecture-centric, iterative — inception, elaboration, construction, transition phases.
  • Concurrent: activities parallel states mein chalti hain (jaise design ka ek part coding ke saath) — large/client-server systems ke liye.

Generic activities thodi detail mein: communication mein problems, requirements, expectations aur business objectives samjho; planning mein kya/kaun/kitna-time/resources/risks decide karo; modeling mein requirements analysis, architecture, database, UI aur component design aata hai; construction = coding + testing; deployment mein installation, training, feedback aur maintenance — feedback wapas communication mein jaata hai.

Do models aur pakke karo: Waterfall ke fayde (simple, clear documentation, easy management) aur nuksaan (change mushkil, late feedback, late software) — stable-requirements projects ke liye. Incremental ka e-commerce example: Increment-1 login, 2 products, 3 cart, 4 payment — fayde: early delivery, feedback, kam risk. Spiral har loop mein risk analysis karta hai (planning → risk → engineering → evaluation) — bade risky projects ke liye, par costly aur complex. V-model mein har development step ka testing pair hota hai (requirements↔acceptance, system-design↔system-testing, architecture↔integration, module↔unit) — testing planning saath-saath chalti hai.

Exam-ready plan: pehle generic model ki 5 activities, phir har prescriptive model ek line flow + best-for + weakness, end mein FIG.001 diagram. “Best-for + weakness” wali line hi examiner ko impress karti hai.

THEORY · Q3

Agile vs plan-driven development

QUESTION

Explain Agile Software Development and compare plan-driven development with agile development.

ANSWER

Agile iterative-incremental approach hai jo manifesto par chalta hai: individuals and interactions (processes se upar), working software (documentation se upar), customer collaboration (contract se upar), responding to change (plan se upar). Kaam chhote time-boxed iterations (sprints) mein hota hai; har sprint working software deta hai aur customer feedback next sprint mein jaata hai.

Exam table / plan-driven vs agile
PointPlan-drivenAgile
RequirementsShuru mein fixed, change costlyWelcome change, backlog evolve hota hai
DeliveryEnd mein poora systemHar sprint mein working increment
CustomerShuru aur end mein milta haiHar sprint mein involved + feedback
DocumentationHeavy, upfrontLight, jitni zaroorat ho
Best forFixed-scope, regulated systemsChanging needs, product development

Agile tools ek line mein: JIRA (backlog/sprint/issue tracking) aur Kanban board (To-Do → Doing → Done columns se flow visualize). Case studies (mental health-care system, wilderness weather system) se ye seekh milti hai ki alag domains mein process tailoring chahiye — ek hi model har jagah fit nahi hota.

Agile cycle order mein yaad karo: requirement → iteration planning → development → testing → working software → customer feedback → next iteration. Characteristics: iterative (chhote sprints, jaise Sprint-1 login, Sprint-2 search), customer collaboration (regular feedback), change welcome (change failure nahi), frequent delivery, continuous testing (end ka wait nahi). Instagram example: plan-driven mein poora design→code→test→release ek baar; Agile mein Sprint-1 login, 2 profile, 3 posts, 4 comments, 5 notifications — har sprint ke baad user feedback.

Exam-ready plan: Agile definition + manifesto 4 values, phir 5-row comparison table, phir JIRA/Kanban ek line, end mein FIG.002 loop diagram.

THEORY · Q4

Extreme Programming (XP)

QUESTION

Explain Extreme Programming (XP) practices, testing in XP, and pair programming.

ANSWER

XP ek lightweight Agile methodology hai jo best practices ko “extreme” level tak le jaati hai — feedback loops chhote, courage zyada. Core practices:

  • Planning game + small releases: customer stories likhta hai, team estimate karti hai; chhote frequent releases se feedback fast milta hai.
  • Simple design + refactoring: aaj ki need ka simplest design; code ko continuously saaf karte raho (behaviour same, structure better).
  • Test-driven development: pehle automated test likho (jo fail hoga), phir code likho jo use pass kare — testing design ko drive karti hai.
  • Continuous integration: din mein kai baar code integrate + automated build/test — conflicts jaldi pakde jaate hain.
  • Collective ownership + coding standards: koi bhi code kahi bhi sudhar sakta hai; common standards se readability bani rehti hai.
  • Sustainable pace + on-site customer: overtime nahi, customer team ke saath — doubt turant clear.

Testing in XP: unit tests programmers likhte hain (TDD), acceptance tests customer define karta hai; dono automated aur har integration par chalte hain. Testing phase nahi, continuous activity hai.

Pair programming: do programmers ek machine par — ek driver (code likhta hai), ek navigator (review + sochta hai); roles rotate hote hain. Fayde: real-time review (defects turant pakde jaate hain), knowledge sharing (bus factor kam), better design. Cost: do log ek kaam par — par defect-fix cost se sasta padta hai.

Aur 3 practices detail mein: TDD cycle — test likho → fail hoga → code likho → pass hoga → refactor (repeat); small releases — sab kuch ek saath nahi, chhote working versions frequently; refactoring — bahar ka behaviour same, andar ka code saaf (complex code → maintainable code). Pair programming ke fayde list karo: continuous review, kam defects, knowledge sharing, better design, ek developer par dependency kam.

Exam-ready plan: XP definition + 5–6 practices bullets, testing para (TDD + acceptance + continuous), pair programming (driver/navigator + 2 fayde), end mein ek-line tradeoff.

THEORY · Q5

Requirements ke types

QUESTION

Explain Software Requirements Engineering and differentiate between user, system, functional, and non-functional requirements.

ANSWER

Requirements Engineering (RE) stakeholder needs ko discover, analyse, document aur maintain karne ka process hai. Galat ya adhuri requirements sabse costly defects deti hain — isliye RE poore process ki neev hai.

Exam table / requirements ke 4 types
TypeKiske liye / languageExample
User requirementsCustomer ke liye, simple natural language“System se fees receipt niklni chahiye”
System requirementsDevelopers ke liye, detailed + precise“Receipt mein roll no., date, amount, signature block hoga”
FunctionalSystem kya karega (services/features)Login, report generation, order placement
Non-functionalSystem kaisa hoga (quality/constraints)Performance, security, usability, reliability

Yaad rakhne ka formula: user vs system = audience aur detail ka farq (customer-language vs developer-language); functional vs non-functional = what vs how-well ka farq. Non-functional ko measurable likho (“fast” nahi, “2 sec mein response” likho) — yehi exam mein extra mark dilata hai.

Banking examples se pakka karo: user requirement — “user dusre account mein paise bhej sake” (simple language); system requirement — “authenticated customer ₹1–₹1,00,000 registered beneficiary ko bhej sake” (exact + measurable). Functional list: login, registration, search, payment, report, order placement. Non-functional list: performance, security, reliability, usability, scalability, availability. Comparison ek line mein: user = user-level need (ticket book ho), system = technical detail (booking ID generate ho), functional = kya karta hai (invoice banao), non-functional = kitna achha (2 sec response). Yaad rakhne ka formula: Functional → WHAT? Non-functional → HOW WELL? User → user kya chahta hai? System → system kaise dega?

Exam-ready plan: RE definition, phir 4-row table with examples, phir what-vs-how-well + measurable-NFR line, end mein FIG.003.

THEORY · Q6

SRS: structure aur likhne ke tareeke

QUESTION

Explain Software Requirements Specification (SRS), its structure, and different ways of writing an SRS.

ANSWER

SRS requirements ka official written document hai — customer aur team ke beech contract jaisa. Iske bina “system complete hua ya nahi” judge hi nahi ho sakta. Achhi SRS correct, complete, consistent, verifiable aur modifiable hoti hai.

Structure (IEEE-style, exam mein headings likho):

  • 1. Introduction: purpose, scope, definitions, references — document kis system ke liye, kyun.
  • 2. Overall description: product perspective, user classes, constraints, assumptions — bada picture.
  • 3. Specific requirements: functional (features), non-functional (performance, security), interfaces (user/hardware/software) — asli detail.
  • Appendix: models, index, open issues (TBD list).

Likhne ke tareeke: natural language (simple, par ambiguity ka risk), structured language (forms/templates + controlled vocabulary — best balance), tabular/graphical (tables, use-case diagrams — insulin pump case study mein structured + tabular SRS se har condition exact likhi gayi), formal/mathematical (precise, par sabko samajh nahi aata — critical systems mein).

SRS ka purpose 6 roles se samjho: developers (kya banana hai), customers (verify karna), testers (test cases), managers (effort estimate), designers (architecture), aur change management (impact track). Structure thoda aur detail mein: introduction (purpose, scope, definitions, references, overview), overall description (perspective, functions, user classes, environment, constraints, assumptions), specific requirements (functional + non-functional + interfaces), appendix (models, TBD list). Structured SRS ka example (FR-01 User Login): Input = email + password; Processing = credentials validate; Output = login success/failed — isi format se ambiguity khatm hoti hai.

Exam-ready plan: SRS definition + 5 qualities, phir 4-part structure headings, phir 4 writing ways with tradeoff, insulin-pump example line.

THEORY · Q7

Elicitation, analysis, validation, management

QUESTION

Explain requirements elicitation, analysis, validation, and requirements management.

ANSWER

Requirements apne aap collect nahi hoti — spiral view mein ye activities baar-baar ghoomti hain jab tak requirements stable na hon:

  • Elicitation (collect): stakeholders se requirements nikaalna — interviews, questionnaires, workshops, observation, prototypes, document study. Technique stakeholder ke hisaab se chuno (busy manager → questionnaire, confused user → prototype).
  • Analysis (samjho + sort): collected needs ko classify (functional/non-functional), conflicts solve, priority lagao, feasibility check. Yahan spiral ghumta hai — unclear points wapas elicitation mein jaate hain.
  • Validation (verify): requirements sahi, complete aur consistent hain ya nahi — reviews, checklists, test-cases likhkar (har requirement testable honi chahiye), prototype demo. Error yahin pakadna sabse sasta hai.
  • Management (sambhalo): change control — har change request evaluate karo (cost/impact), approve ho toh documents + traceability update karo, versions maintain karo. Bina management ke scope creep project dubota hai.

Sources aur techniques detail mein: requirements customers, users, managers, domain experts, regulations aur existing systems se aati hain. Technique stakeholder dekhkar chuno — interviews (direct sawal), questionnaires (bahut users hon tab), observation (actual kaam dekhna), workshops (sab stakeholders saath), prototyping (pehla rough version banakar confusion clear). Analysis mein conflicts pakdo — jaise Customer A “login mein password chahiye”, Customer B “password nahi chahiye” — resolve kiye bina aage mat badho. Validation checklist: correct, complete, consistent, feasible, unambiguous, testable. Bad requirement “bahut fast hona chahiye” ko aise sudharo: “95% requests ka response 2 sec mein” — measurable = testable. Management flow: change request → impact analysis → approval → documents update → design/code/test changes.

Exam-ready plan: spiral-view line se start, phir 4 activities har ek: matlab + 1 technique/example, end mein “validation sabse sasta fix, management scope-creep rokta hai” wali closing line.

THEORY · Q8

Design process, concepts, models, patterns

QUESTION

Explain the software design process, design concepts, design models, and pattern-based software design.

ANSWER

Design process requirements (“kya banana hai”) ko blueprint (“kaise banana hai”) mein badalta hai. Quality wali design ke liye process + concepts dono chahiye:

  • Design concepts: abstraction (detail chhupao), modularity (chhote parts), information hiding (andar ka data private), coupling kam + cohesion zyada (modules independent par internally focused hon), refinement (step-by-step detail badhao).
  • Design model ke 4 views: data design (structures), architectural design (bada structure), interface design (andar-bahar connection), component design (har piece ka detail) — ye Q9 mein expand honge.
  • Pattern-based design: repeated problems ke proven solutions reuse karo (jaise login-session ke liye known pattern) — design time bachta hai aur reliability milti hai, kyunki pattern pehle test ho chuka hai.

Design process 5 steps mein: requirements analyse karo → architectural design (overall structure) → data design (entities, relations, storage) → interface design (user-system, component-component, external) → component design (har module/class ka detail). Cohesion-coupling payment example se samjho: Payment Module mein processing + validation + confirmation (closely related = high cohesion, good); agar Module A har chhoti baat ke liye Module B par depend kare toh coupling high = bad. Models: architectural (bade blocks), data (structures), interface (communication), component (pieces), class (classes + relations). Famous patterns: Singleton (sirf ek instance), Factory (object creation logic chhupao), Observer (subject badle toh observers ko notify) — fayde: reuse, maintainability, common vocabulary, kam effort.

Exam-ready plan: design = requirements-to-blueprint line, phir 5 concepts with one-line meaning, phir 4 model views, phir pattern = proven-solution-reuse line.

THEORY · Q9

Architectural + component-level design

QUESTION

Explain architectural design and component-level design with suitable examples.

ANSWER

Architectural design system ka overall structure hai — bade blocks (components) + unke connections + decisions (views, patterns, application architectures jaise layered, client-server, MVC). Example: online shop mein presentation layer, business-logic layer, database layer — har layer ki responsibility fixed, layers ke beech defined interfaces.

Component-level design har block ke andar ka detail hai — class-based components: attributes (data), operations (methods), interfaces. Example: Cart class mein attributes items/total, operations addItem()/checkout(), aur payment-gateway interface. Conducting it = har component ka data + behaviour + collaboration likhna.

Exam-ready plan: architecture = blocks + connections + layered example, component = class detail + Cart example, FIG.004 levels, end mein “architecture decides shape, components fill it” line.

E-commerce architecture sketch yaad karo: User → UI → API Gateway → User/Product/Order services → Database (payment bahar gateway se). 3 styles: layered (presentation → logic → data-access → DB; fayda: separation, maintenance), client-server (browser → server → DB), MVC (User → View → Controller → Model → DB). OrderService ka component detail: createOrder(), validateOrder(), calculateTotal(), applyDiscount(), cancelOrder() — interfaces, classes, methods, data structures sab define hote hain. Arch-vs-component table: high-level vs detailed, structure vs pieces, modules vs classes/functions, relationships vs logic. Yaad rakhne ke liye: Architecture = Building Plan, Component = Room Design.

THEORY · Q10

UI design, UML diagrams, testing types

QUESTION

Explain User Interface Design, UML diagrams, and different types of software testing.

ANSWER

UI design (golden rules): user control mein rahe (undo, clear options), memory load kam karo (sab yaad mat karao, dikhao), consistency rakho (same action, same look). Steps: user analysis (kaun use karega) → prototype → evaluation (real users se test) → refine. Design evaluation = usability testing + feedback loop.

UML (Unified Modeling Language): system ko pictures mein model karne ki standard language. Do families:

  • Structural (static): class diagram (classes + relations), use-case diagram (actors + goals), deployment diagram (hardware par software kahan chalega).
  • Behavioral (dynamic): sequence diagram (time ke saath object interactions — MCQ 19 ka answer), activity/state diagrams (flow aur states).

Testing types (levels + techniques): unit testing (single component in isolation — MCQ 20), integration testing (connected modules saath mein), system testing (poora system requirements par), acceptance testing (customer approval). Techniques: black-box (bina code dekhe input-output) vs white-box (code paths dekhkar).

UI process chain order mein: users samjho → tasks pehchano → interface design → prototype → evaluate → improve. 5 principles examples ke saath: consistency (sab buttons ek jaise), simplicity (extra complexity hatao), feedback (“Save” → “File saved successfully”), error prevention (galti hone hi na do), user control (undo/cancel/back/delete-confirmation). UML 6 diagrams: use-case (Customer → login/search/cart/order), class (Customer: name/email + login()/logout()), sequence (User → Login UI → Auth → DB → wapas chain), activity (login → validate → Yes-Home/No-Error), state (Created → Pending → Shipped → Delivered), deployment (Mobile → Web → App → DB servers). Testing 7 types: unit (calculate_total() akela), integration (login + database), system (login → search → cart → payment → order poora flow), acceptance (customer approval), regression (nayi feature ke baad purane tests), performance (response/throughput/scalability), security (unauthorized access, injection). Levels yaad rakhne ka chain: Unit → Integration → System → Acceptance.

Reference depth for Q10: UI process chain order mein — users samjho → tasks pehchano → interface design → prototype → evaluate → improve. 5 principles examples ke saath: consistency (ek jaise buttons), simplicity (extra complexity hatao), feedback (“Save” → “File saved successfully”), error prevention (galti hone hi na do), user control (undo/cancel/back/delete-confirmation). 6 UML diagrams: use-case (Customer → login/search/cart/order), class (Customer: name/email + login()/logout()), sequence (User → Login UI → Auth → DB → wapas chain), activity (login → validate → Yes-Home/No-Error), state (Created → Pending → Shipped → Delivered), deployment (Mobile → Web → App → DB servers). 7 testing types: unit (calculate_total() akela), integration (login + database), system (poora login→order flow), acceptance (customer approval), regression (nayi feature ke baad purane tests), performance (response/throughput/scalability), security (unauthorized access, injection). Level chain: Unit → Integration → System → Acceptance.

    A) Agile · B) Waterfall · C) Spiral · D) Concurrent

    A) Rapid Application Development · B) Random Application Design · C) Requirement Analysis Development · D) Rapid Algorithm Design
    Answer: A — components + time-boxing se fast delivery.

  6. Q6. Which model develops software in increments?

    A) Incremental · B) Waterfall · C) V-Model · D) Big Bang
    Answer: A — har increment working subset hota hai.

  7. Q7. Agile mainly emphasizes?

    A) Documentation only · B) Customer collaboration and responding to change · C) Avoiding feedback · D) Fixed requirements

  8. Q8. Which is an Agile methodology?

    A) Extreme Programming · B) Waterfall · C) Big Bang · D) V-Model
    Answer: A — XP lightweight Agile methodology hai.

  9. Q9. In XP, pair programming involves?

    A) Two independent teams · B) Two programmers on the same task · C) Testing without coding · D) One programmer, two projects
    Answer: B — driver + navigator, same machine.

  10. Q10. JIRA is commonly used for?

    A) Image processing · B) Project and issue management · C) OS development · D) Hardware design
    Answer: B — backlog/sprint/issue tracking tool.

  11. Q11. A functional requirement specifies?

    A) What the system should do · B) Programming language only · C) Development cost only · D) Physical size
    Answer: A — functional = system kya karega.

  12. Q12. Which is a non-functional requirement?

    A) User login · B) Report generation · C) System performance · D) Order placement
    Answer: C — non-functional = system kaisa hoga (quality).

  13. Q13. SRS stands for?

    A) Software Requirement Specification · B) System Resource Software · C) Software Resource System · D) System Requirement Structure
    Answer: A — (standard spelling “Requirements” plural hoti hai; QB option singular mein hai, answer phir bhi A).

  14. Q14. Requirements validation ensures requirements are?

    A) Expensive · B) Correct, complete, and consistent · C) Difficult · D) Written only by programmers
    Answer: B — validation = sahi + poori + consistent.

  15. Q15. Which activity collects requirements from stakeholders?

    A) Requirements elicitation · B) Coding · C) Deployment · D) Refactoring
    Answer: A — elicitation = collect karna.

  16. Q16. Which is a software design concept?

    A) Modularity · B) Compilation · C) Debugging only · D) Installation
    Answer: A — modularity core design concept hai.

  17. Q17. Architectural design primarily describes?

    A) Detailed source code · B) Overall structure of the system · C) User passwords · D) Test data only
    Answer: B — architecture = bada structure.

  18. Q18. UML stands for?

    A) Unified Modeling Language · B) Universal Machine Language · C) User Management Language · D) Unified Machine Logic
    Answer: A — standard modeling language.

  19. Q19. Which UML diagram shows interactions over time?

    A) Class · B) Sequence · C) Use-case · D) Deployment
    Answer: B — sequence diagram time-order mein objects dikhata hai.

  20. Q20. Which technique examines individual components?

    A) System · B) Acceptance · C) Unit · D) Integration

THEORY · Q1

Nature of software and SE principles

QUESTION

Explain the nature of software and the fundamental principles of Software Engineering.

ANSWER

The nature of software is totally unlike hardware — and that nature is exactly why Software Engineering is needed. First the characteristics:

  • Intangible: cannot be touched; understood only via code, documents, and behaviour. Hence progress is hard to measure.
  • Developed, not manufactured: hardware is built in factories; software is developed once and then copied. Cost lies in design, not production.
  • Does not wear out physically: never degrades with time, but fails through obsolescence as environment changes (OS, hardware, needs) — think “obsolescence curve”, not a bath-tub.
  • Complexity and change: today's systems run into lakhs of lines and requirements always evolve — unmanageable without engineering discipline.

Fundamental principles (write these 4–5 in the exam):

  • Separation of concerns: break big problems into small independent parts (basis of modularity).
  • Abstraction: hide detail, show only the needed view (like a function name, not its code).
  • Modularity + information hiding: each module does one job and keeps its internal data private.
  • Incremental + iterative development: build in small pieces, take feedback, improve.
  • Documentation and measurement: write decisions down, measure progress — control is impossible without this.
  • Reusability: reuse libraries, APIs, frameworks — saves time, fewer defects.
  • Maintainability: design software so bug fixes, features, and updates happen without rewrites.

Lock the reference examples too: manufactured vs developed — a laptop is manufactured, but Windows/Android/a banking app is developed (cost sits in design + maintenance). Wear-out: hardware degrades from heat/stress/age; software breaks through modification (new feature → unexpected bug → more modification). Abstraction: using sort(data) needs no knowledge of the inner algorithm. Complexity: an e-commerce app's UI, auth, product, payment, order, database, and notification services — managing this is exactly why SE exists. Formal touch: Mitchell's Task/Performance/Experience definition of learning.

EXAM DEFINITION

Software Engineering is the systematic, disciplined, quantifiable approach to the development, operation, and maintenance of software.

Exam-ready plan: first 4 characteristics (intangible, developed-not-manufactured, no physical wear, complexity/change), then 4–5 principles with one-line meanings, ending with the SE definition. Both characteristics and principles are asked — missing either costs half the marks.

THEORY · Q2

Generic + prescriptive process models

QUESTION

Explain the generic process model and different prescriptive process models.

ANSWER

The generic process model is the common framework of every software process — 5 activities: communication (understand requirements), planning (schedule/resources), modeling (build the design), construction (code + test), deployment (deliver + feedback). Every prescriptive model arranges these 5 in a different flow.

Prescriptive models (for each: flow + best-for + weakness):

  • Waterfall: strictly sequential — next phase only after the previous completes. Best when requirements are fixed and clear (e.g. payroll system). Weakness: change is costly, working software comes only at the end.
  • Incremental (RAD): software delivered in pieces (increments); each increment is a working subset. RAD uses components + time-boxing for fast delivery. Best when early partial delivery is wanted.
  • Evolutionary (Prototyping/Spiral): build prototype → feedback → refine; or spiral with risk analysis in every loop. Best when requirements are unclear.
  • Unified Process (UP): use-case driven, architecture-centric, iterative — inception, elaboration, construction, transition phases.
  • Concurrent: activities run in parallel states (e.g. part of design with coding) — for large/client-server systems.

Expand the generic activities a little: in communication grasp problems, requirements, expectations, and business objectives; in planning decide what/who/how-long/resources/risks; modeling covers requirements analysis, architecture, database, UI, and component design; construction = coding + testing; deployment covers installation, training, feedback, and maintenance — feedback loops back into communication.

Fix two more models firmly: Waterfall's strengths (simple, clear documentation, easy management) and weaknesses (change is hard, late feedback, late software) — for stable-requirement projects. Incremental's e-commerce example: Increment-1 login, 2 products, 3 cart, 4 payment — benefits: early delivery, feedback, lower risk. Spiral analyses risk every loop (planning → risk → engineering → evaluation) — for big risky projects, but costly and complex. In the V-model every development step has a testing pair (requirements↔acceptance, system-design↔system-testing, architecture↔integration, module↔unit) — test planning runs side by side.

Exam-ready plan: first the generic model's 5 activities, then each prescriptive model in one line of flow + best-for + weakness, ending with the FIG.001 diagram. The “best-for + weakness” line is what impresses the examiner.

THEORY · Q3

Agile vs plan-driven development

QUESTION

Explain Agile Software Development and compare plan-driven development with agile development.

ANSWER

Agile is an iterative-incremental approach running on its manifesto: individuals and interactions (over processes), working software (over documentation), customer collaboration (over contracts), responding to change (over plans). Work happens in small time-boxed iterations (sprints); every sprint delivers working software, and customer feedback feeds the next sprint.

Exam table / plan-driven vs agile
PointPlan-drivenAgile
RequirementsFixed upfront, change is costlyChange welcomed, backlog evolves
DeliveryFull system at the endWorking increment every sprint
CustomerMet at start and endInvolved every sprint + feedback
DocumentationHeavy, upfrontLight, as needed
Best forFixed-scope, regulated systemsChanging needs, product development

Agile tools in one line: JIRA (backlog/sprint/issue tracking) and Kanban board (To-Do → Doing → Done columns visualizing flow). The case studies (mental health-care system, wilderness weather system) teach that different domains need process tailoring — one model never fits everywhere.

Memorize the Agile cycle in order: requirement → iteration planning → development → testing → working software → customer feedback → next iteration. Characteristics: iterative (short sprints, e.g. Sprint-1 login, Sprint-2 search), customer collaboration (regular feedback), welcomed change (change is not failure), frequent delivery, continuous testing (no end-phase wait). Instagram example: plan-driven does full design→code→test→release once; Agile does Sprint-1 login, 2 profile, 3 posts, 4 comments, 5 notifications — user feedback after every sprint.

Exam-ready plan: Agile definition + 4 manifesto values, then the 5-row comparison table, then JIRA/Kanban in one line, ending with the FIG.002 loop diagram.

THEORY · Q4

Extreme Programming (XP)

QUESTION

Explain Extreme Programming (XP) practices, testing in XP, and pair programming.

ANSWER

XP is a lightweight Agile methodology that takes best practices to “extreme” levels — short feedback loops, high courage. Core practices:

  • Planning game + small releases: customer writes stories, team estimates; small frequent releases get fast feedback.
  • Simple design + refactoring: simplest design for today's need; continuously clean code (same behaviour, better structure).
  • Test-driven development: write the automated test first (it will fail), then write code that passes it — testing drives design.
  • Continuous integration: integrate code + automated build/test several times a day — conflicts get caught early.
  • Collective ownership + coding standards: anyone may improve any code; common standards keep readability.
  • Sustainable pace + on-site customer: no overtime, customer sits with the team — doubts clear instantly.

Testing in XP: programmers write unit tests (TDD), customers define acceptance tests; both automated and run on every integration. Testing is a continuous activity, not a phase.

Pair programming: two programmers on one machine — a driver (writes code) and a navigator (reviews + thinks); roles rotate. Benefits: real-time review (defects caught instantly), knowledge sharing (lower bus factor), better design. Cost: two people on one task — but cheaper than defect-fixing cost.

Three more practices in detail: the TDD cycle — write test → it fails → write code → it passes → refactor (repeat); small releases — frequent small working versions instead of everything at once; refactoring — same outside behaviour, cleaner inside (complex code → maintainable code). List pair programming's benefits: continuous review, fewer defects, knowledge sharing, better design, less dependence on one developer.

Exam-ready plan: XP definition + 5–6 practice bullets, testing para (TDD + acceptance + continuous), pair programming (driver/navigator + 2 benefits), ending with a one-line tradeoff.

THEORY · Q5

Types of requirements

QUESTION

Explain Software Requirements Engineering and differentiate between user, system, functional, and non-functional requirements.

ANSWER

Requirements Engineering (RE) is the process of discovering, analysing, documenting, and maintaining stakeholder needs. Wrong or incomplete requirements cause the costliest defects — which is why RE is the foundation of the whole process.

Exam table / 4 types of requirements
TypeFor whom / languageExample
User requirementsFor customers, simple natural language“Fee receipts should come out of the system”
System requirementsFor developers, detailed + precise“Receipt will carry roll no., date, amount, signature block”
FunctionalWhat the system does (services/features)Login, report generation, order placement
Non-functionalHow well the system behaves (quality/constraints)Performance, security, usability, reliability

The memorizing formula: user vs system = difference of audience and detail (customer-language vs developer-language); functional vs non-functional = difference of what vs how-well. Write non-functionals measurably (not “fast” but “responds in 2 sec”) — that line earns the extra mark.

Fix the banking examples: user requirement — “the user should be able to transfer money to another account” (simple language); system requirement — “authenticated customers may transfer ₹1–₹1,00,000 to a registered beneficiary” (exact + measurable). Functional list: login, registration, search, payment, report, order placement. Non-functional list: performance, security, reliability, usability, scalability, availability. One-line comparison: user = user-level need (book a ticket), system = technical detail (generate booking ID), functional = what it does (generate invoice), non-functional = how well (2-sec response). Memory formula: Functional → WHAT? Non-functional → HOW WELL? User → what does the user want? System → how must the system provide it?

THEORY · Q6

SRS: structure and writing styles

QUESTION

Explain Software Requirements Specification (SRS), its structure, and different ways of writing an SRS.

ANSWER

SRS is the official written document of requirements — like a contract between customer and team. Without it, “is the system complete or not” cannot even be judged. A good SRS is correct, complete, consistent, verifiable, and modifiable.

Structure (IEEE-style, write these headings in the exam):

  • 1. Introduction: purpose, scope, definitions, references — which system, and why.
  • 2. Overall description: product perspective, user classes, constraints, assumptions — the big picture.
  • 3. Specific requirements: functional (features), non-functional (performance, security), interfaces (user/hardware/software) — the real detail.
  • Appendix: models, index, open issues (TBD list).

Ways of writing: natural language (simple, but ambiguity risk), structured language (forms/templates + controlled vocabulary — best balance), tabular/graphical (tables, use-case diagrams — the insulin-pump case study wrote every condition exactly with structured + tabular SRS), formal/mathematical (precise, but not everyone understands it — for critical systems).

Exam-ready plan: SRS definition + 5 qualities, then the 4-part structure headings, then 4 writing styles with tradeoffs, insulin-pump example line.

Expand with the reference detail: an SRS serves 6 roles — developers (what to build), customers (verify), testers (test cases), managers (effort estimates), designers (architecture), change control (impact tracking). Structure in a bit more detail: introduction (purpose, scope, definitions, references, overview), overall description (perspective, functions, user classes, environment, constraints, assumptions), specific requirements (functional + non-functional + interfaces), appendix (models, TBD list). Structured SRS example (FR-01 User Login): Input = email + password; Processing = validate credentials; Output = login success/failed — this format kills ambiguity.

THEORY · Q7

Elicitation, analysis, validation, management

QUESTION

Explain requirements elicitation, analysis, validation, and requirements management.

ANSWER

Requirements never collect themselves — in the spiral view these activities keep looping until requirements stabilize:

  • Elicitation (collect): extracting requirements from stakeholders — interviews, questionnaires, workshops, observation, prototypes, document study. Pick the technique by stakeholder (busy manager → questionnaire, confused user → prototype).
  • Analysis (understand + sort): classify collected needs (functional/non-functional), resolve conflicts, prioritize, feasibility check. The spiral turns here — unclear points go back to elicitation.
  • Validation (verify): checking requirements are correct, complete, and consistent — reviews, checklists, writing test cases (every requirement must be testable), prototype demo. Catching errors here is the cheapest.
  • Management (maintain): change control — evaluate every change request (cost/impact), and on approval update documents + traceability, maintain versions. Without management, scope creep sinks the project.

Exam-ready plan: start with the spiral-view line, then 4 activities each with meaning + 1 technique/example, ending with the closing line “validation is the cheapest fix, management stops scope creep”.

Detail from the reference: requirements come from customers, users, managers, domain experts, regulations, and existing systems. Pick techniques by stakeholder — interviews (direct questions), questionnaires (many users), observation (watch real work), workshops (all stakeholders together), prototyping (rough version to clear confusion). In analysis, catch conflicts — e.g. Customer A “login needs a password” vs Customer B “no password” — never proceed unresolved. Validation checklist: correct, complete, consistent, feasible, unambiguous, testable. Fix bad requirements like “very fast” into “responds in 2 sec for 95% requests” — measurable = testable. Management flow: change request → impact analysis → approval → documents update → design/code/test changes.

THEORY · Q8

Design process, concepts, models, patterns

QUESTION

Explain the software design process, design concepts, design models, and pattern-based software design.

ANSWER

The design process converts requirements (“what to build”) into a blueprint (“how to build it”). Quality design needs both process and concepts:

  • Design concepts: abstraction (hide detail), modularity (small parts), information hiding (internal data private), low coupling + high cohesion (modules independent yet internally focused), refinement (add detail step by step).
  • Design model's 4 views: data design (structures), architectural design (big structure), interface design (inside-outside connections), component design (detail of each piece) — expanded in Q9.
  • Pattern-based design: reuse proven solutions of repeated problems (like a known pattern for login sessions) — saves design time and brings reliability, because the pattern is already tested.

Exam-ready plan: design = requirements-to-blueprint line, then 5 concepts with one-line meanings, then 4 model views, then the pattern = proven-solution-reuse line.

Reference detail for depth: the 5-step design process — analyse requirements → architectural design (overall structure) → data design (entities, relations, storage) → interface design (user-system, component-component, external) → component design (each module/class in detail). Cohesion–coupling via the payment example: processing + validation + confirmation together (closely related = high cohesion, good); Module A depending on Module B for everything (high coupling = bad). Models: architectural (big blocks), data (structures), interface (communication), component (pieces), class (classes + relations). Famous patterns: Singleton (only one instance), Factory (hide creation logic), Observer (subject changes → notify observers) — benefits: reuse, maintainability, common vocabulary, less effort.

THEORY · Q9

Architectural + component-level design

QUESTION

Explain architectural design and component-level design with suitable examples.

ANSWER

Architectural design is the system's overall structure — big blocks (components) + their connections + decisions (views, patterns, application architectures like layered, client-server, MVC). Example: in an online shop, the presentation layer, business-logic layer, and database layer — each layer with fixed responsibility and defined interfaces between layers.

Component-level design is the detail inside each block — class-based components: attributes (data), operations (methods), interfaces. Example: a Cart class with attributes items/total, operations addItem()/checkout(), and a payment-gateway interface. Conducting it = writing every component's data + behaviour + collaboration.

Exam-ready plan: architecture = blocks + connections + layered example, component = class detail + Cart example, FIG.004 levels, ending with the “architecture decides shape, components fill it” line.

Memorize the e-commerce architecture sketch: User → UI → API Gateway → User/Product/Order services → Database (payment via outside gateway). 3 styles: layered (presentation → logic → data-access → DB; benefit: separation, maintenance), client-server (browser → server → DB), MVC (User → View → Controller → Model → DB). OrderService component detail: createOrder(), validateOrder(), calculateTotal(), applyDiscount(), cancelOrder() — interfaces, classes, methods, and data structures all get defined. Arch-vs-component table: high-level vs detailed, structure vs pieces, modules vs classes/functions, relationships vs logic. Remember: Architecture = Building Plan, Component = Room Design.

THEORY · Q10

UI design, UML diagrams, testing types

QUESTION

Explain User Interface Design, UML diagrams, and different types of software testing.

ANSWER

UI design (golden rules): keep the user in control (undo, clear options), reduce memory load (show, don't make them memorize), stay consistent (same action, same look). Steps: user analysis (who will use it) → prototype → evaluation (test with real users) → refine. Design evaluation = usability testing + feedback loop.

UML (Unified Modeling Language): the standard language for modeling a system in pictures. Two families:

  • Structural (static): class diagram (classes + relations), use-case diagram (actors + goals), deployment diagram (where software runs on hardware).
  • Behavioral (dynamic): sequence diagram (object interactions over time — the answer to MCQ 19), activity/state diagrams (flows and states).

Testing types (levels + techniques): unit testing (single component in isolation — MCQ 20), integration testing (connected modules together), system testing (whole system against requirements), acceptance testing (customer approval). Techniques: black-box (input-output without seeing code) vs white-box (seeing code paths).

Reference depth for Q10: UI process chain in order — understand users → identify tasks → design interface → prototype → evaluate → improve. 5 principles with examples: consistency (uniform buttons), simplicity (no extra complexity), feedback (“Save” → “File saved successfully”), error prevention (don't let errors happen), user control (undo/cancel/back/delete-confirmation). 6 UML diagrams: use-case (Customer → login/search/cart/order), class (Customer: name/email + login()/logout()), sequence (User → Login UI → Auth → DB → back chain), activity (login → validate → Yes-Home/No-Error), state (Created → Pending → Shipped → Delivered), deployment (Mobile → Web → App → DB servers). 7 testing types: unit (calculate_total() alone), integration (login + database), system (full login→order flow), acceptance (customer approval), regression (old tests after new feature), performance (response/throughput/scalability), security (unauthorized access, injection). Level chain: Unit → Integration → System → Acceptance.

Exam-ready plan: UI golden rules (3) + steps, UML 2 families with 2 examples each, testing 4 levels bottom-up + black/white-box, FIG.005 + FIG.006.
